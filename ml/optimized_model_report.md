# Optimized complaint model integration

## Model choice and evaluation

The notebook's final comparison reports the no-SMOTE Logistic Regression as its
category model (97.00% accuracy, 96.95% weighted F1) and Logistic Regression as
its priority model (98.33% accuracy and weighted F1). The separate 100% category
result is the SMOTE model, not the category model selected in that comparison.

The notebook fitted TF-IDF on all 1,500 rows before making its train/test split,
so its reported test scores include vocabulary/IDF leakage. The exported models
were therefore retrained from `cleaned_hotel_maintenance_dataset.csv`. Exact
duplicate complaints were removed before a stratified 80/20 split, and TF-IDF
was fitted only on the 1,160 training rows. The 290-row held-out result is:

| Model | Accuracy | Weighted F1 | Macro F1 |
|---|---:|---:|---:|
| Category | 96.90% | 96.86% | 96.65% |
| Priority | 98.62% | 98.62% | 98.48% |

The category labels are `Electrical`, `Plumbing`, `Structural`, and `General`.
Priority labels remain `High`, `Medium`, and `Low`; they are not renamed to
`urgent`, `routine`, or `cosmetic`. The data contains 50 exact duplicate rows
that were removed. Near-duplicate or source-label bias may remain.

The category targets were generated by the notebook's keyword rules; these
metrics measure agreement with those heuristic labels, not independent human
adjudication. In the deduplicated source data, `urgent` appears in 110/430 High,
114/659 Medium, and 62/361 Low complaints. The cue occurs across all priority
classes, and the notebook did not provide a separate priority leakage audit.

Detailed reports and split metadata are in
[`evaluation/optimized_model_report.json`](./evaluation/optimized_model_report.json).
The current `category_report.json` and `priority_report.json` are refreshed from
the same held-out evaluation. `compute_cm.py` now uses that split and matching
preprocessing. The old `train.py` and `train_hostel.py` write into separate
legacy artifact directories so they cannot overwrite the active models.

## Runtime artifacts and inference

The active fitted objects are `models/tfidf.pkl`, `models/category.pkl`, and
`models/priority.pkl`. They use scikit-learn 1.9.0, joblib 1.5.3, NumPy 2.5.2,
and SciPy 1.18.0. The notebook's NLTK English stop-word list is bundled at
[`resources/nltk_english_stopwords.txt`](./resources/nltk_english_stopwords.txt)
so inference does not need to download NLTK data. Training and inference use
the same text normalization.

`PredictionService.predict(complaint_text)` returns category, priority, and
the maximum class probabilities when available. These values are model
confidence estimates, not calibrated probabilities or guarantees of correctness.
Empty descriptions, descriptions that clean to no words, missing model files,
and prediction failures are surfaced as explicit errors; prediction failures
are logged and are not replaced with guessed labels.

The Electrical and broken-hinge examples still receive the notebook's
misclassified `General` category. The ceiling-fan case does as well.
An additional representative lighting/socket complaint also predicts
`General`, confirming that Electrical recall remains a concern despite strong
aggregate test scores.

## Integration boundary

FastAPI loads the prediction service once during application startup. This
project snapshot has no complaint router, authenticated user identity contract,
or complaint-creation workflow, so this change does not add API/MongoDB writes
or department routing. Those need to be connected when the complaint API and
identity flow are implemented; the present prediction service returns only the
two model labels and confidence estimates.
